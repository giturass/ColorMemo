# 编辑草稿与异常恢复

编辑便签或白板时，标题、正文、颜色、置顶、归档、提醒、白板图层及附件变更会立即进入本机草稿写入队列，不需要等到点击「保存」或退出页面。连续输入时合并尚未开始写入的旧快照，正在执行的写入不会被新输入取消；页面上显示「正在保存草稿…」「草稿已保存到本机」或失败提示。

关机、从最近任务划走、应用崩溃或系统回收进程后，再次打开应用会自动恢复最后成功写入的编辑草稿，包括新建笔记和已有笔记的修改。恢复草稿优先于通知请求打开的另一条笔记。写入失败时保留编辑内容与上一次成功写入的草稿，并提供重试按钮。读取失败时保留原草稿，不用空白编辑覆盖它。

「保存」仍负责把草稿提交为正式笔记，并按设置安排同步。草稿仅存在当前设备，不进入同步、导出备份或本机 AI 接口；它不能代替跨设备备份。「放弃修改」确认后才清除本地草稿，原笔记保留。尚未落盘的最后一次输入，以及还没确认到画布的文字弹窗等临时操作，遇到瞬间断电或进程终止仍可能无法恢复；以页面显示的草稿保存状态为准。

## 实现约束

- 数据库从版本 2 非破坏性迁移至版本 3，新增 `editor_drafts`，保留既有笔记和本机 AI 授权。版本 1 按既有 1→2 迁移后继续迁移。
- 使用 WAL 和 `synchronous=FULL`，提交时要求 SQLite 同步日志到持久存储。草稿 JSON 压缩后存入独立表，附件先写入已有的应用私有附件目录，草稿只记录附件元数据。
- 草稿包含完整的初始版本及当前内容。恢复后保存仍按既有修订合并规则保留远端并发修改。草稿写入不创建笔记修订，不触发同步和提醒调度。
- 编辑数据由应用级控制器持有，页面销毁和旋转不会取消已接受的写入；输入回调直接捕获数据，后台串行写入，没有等待停止输入的防抖计时器。`onPause` 仅补充唤醒和重试，恢复不依赖退出、关机或崩溃回调。
- 正式笔记写入与对应草稿删除属于同一个 Room 事务。保存/放弃与后台草稿写入串行执行，并校验编辑会话编号，防止已结束的草稿被旧回调重新写回。
- 正文、白板和附件不放入 Activity 的 saved-state Bundle，避免大笔记触发 Binder 大小限制；Bundle 只保存轻量界面状态。

## 验证

单元测试覆盖连续输入与合并、写入期间的新输入、写入失败及重试、调用方取消保存、放弃与写入竞争、无法读取的草稿保护、完整版本/附件/白板恢复、并发冲突保留和保存后的草稿清理。

设备验收时分别对新便签、已有便签和包含图片/文字的白板执行：

1. 修改内容，等待出现「草稿已保存到本机」，不点击正式保存。
2. 按 Home 后从最近任务划走、强行停止进程、重启设备，分别重新打开应用，核对恢复内容及附件。
3. 在长时间连续输入或绘画时终止进程，核对恢复到最后成功持久化的快照。
4. 恢复后正式保存，再重启，确认只出现一份正式笔记；选择「放弃修改」后重启，确认草稿不再出现。
5. 编辑期间旋转屏幕、打开图片选择器，确认内容保留；另一设备同时修改后保存，确认两份内容均保留。

2026-10-25 核对的官方资料：

- [Android 保存界面状态](https://developer.android.com/topic/libraries/architecture/saving-states)：本地持久存储可跨进程终止和用户完整关闭保留数据，saved state 不能替代大数据的持久化。
- [Activity 生命周期](https://developer.android.com/guide/components/activities/activity-lifecycle)：后台进程可能直接结束，不能依赖 `onDestroy` 保存数据。
- [SQLite synchronous](https://www.sqlite.org/pragma.html#pragma_synchronous)：WAL 配合 FULL 在每次事务提交时同步 WAL，NORMAL 在断电时可能丢失已提交事务。
- [Room 数据库迁移](https://developer.android.com/training/data-storage/room/migrating-db-versions)：注册明确的迁移路径并导出各版本 schema，升级时保留已有数据，不使用破坏性重建。
